php-epub improvement backlog — 2026-10-12 (round 5)¶

Discovery-only audit of src/, scripts/, docs/, tests/ and .github/workflows/ at b5ce66f (main), after the round-4 backlog was closed (#139-#146) and the web-tools work landed (#147-#153). No source changes were made while compiling this list.

The target was 30. Only 26 items held up after checking, and the list was not padded. No security vulnerabilities were found. ZIP extraction, EpubReader streaming limits, XmlParser, HtmlSanitizer/CssSanitizer and the HTML export's <style> escaping and CSP were re-checked; SEC-01 is hardening. The new modules (Cleanup, Merge, Split, Repair, Kindle, Build, EpubReader) were reviewed as two extra batches.

Execution instructions¶

  • One branch and one PR per theme (see Themes below); stack PRs that touch the same files.
  • Write the failing test first. Build hostile EPUBs inside the test (tests/Support/EpubBuilder) rather than committing binary fixtures.
  • Before every push run the gates against fresh dependencies, as CI does (composer update, composer quality, then git checkout composer.lock), and check each exit code.
  • Tick the box here in the same PR that fixes an item. Delete docs/improvement-audit/ once every item is done or explicitly declined (list declined items in that PR's description).

Security hardening¶

  • [ ] SEC-01 Add a compressed-size cap (Limits::$maxArchiveBytes, set in web()) enforced while openStream()/openString() buffer the archive, in EpubFile and EpubReader — src/EpubFile.php:118-133, src/EpubReader.php:140-160, src/Limits.php:17-35 — S · med openStream() copies the whole stream to a scratch file with an unbounded stream_copy_to_stream() before any limit applies, so Limits::web() cannot stop a multi-gigabyte request body from filling the temp disk. Callers usually cap uploads, so this is hardening, not a vulnerability.
